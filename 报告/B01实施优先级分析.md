# B01 多模态数据语义理解：实施任务合理优先级分析

## 一、排序依据

以下排序以“实验室资源能够满足 B01 复赛本地部署”为前提，依据四个事实制定：

1. B01 初赛只评测两项：单模态语义理解 40 分、跨模态数据对齐关联 60 分。
2. B01 不提供训练数据，参赛队必须自行搜集、清洗、标注并组织训练数据。
3. 复赛才增加多模态联合分析 30 分、技术方案 20 分、智能体演示 10 分和时效性 10 分。
4. 所有测试答案必须由符合参数限制的本地模型产生，不能用闭源在线模型或测试样例特判替代模型推理。

因此，第一阶段不能先追求“完整大模型智能体”或演示效果，而应先建立可测量的数据和算法主线，优先拿下初赛两项分数。

---

## 二、总优先级排序

| 优先级 | 工作项 | 主要目的 | 建议时点 |
|---|---|---|---|
| 0 | 规则、接口和合规边界冻结 | 避免模型选型和输出格式返工 | 立即完成 |
| 1 | 自建数据集与评测基准 | 解决 B01 最大的先决条件，支撑全部算法 | 与基线并行，最早启动 |
| 2 | 最小可运行端到端基线 | 尽早打通输入、推理、输出、评分和错误定位 | 第一阶段完成 |
| 3 | 单模态航迹语义理解 | 初赛 40 分，也是跨模态关联的基础 | 优先做出稳定版本 |
| 4 | 跨模态数据对齐关联 | 初赛 60 分，初赛得分的最大来源 | 单模态表征稳定后重点攻关 |
| 5 | 轨迹分析工具和智能体编排 | 提升轨迹理解可控性、可解释性和可扩展性 | 主线稳定后逐步加入 |
| 6 | 多模态联合分析 | 复赛新增 30 分，依赖前两项能力 | 初赛方案稳定后投入 |
| 7 | 离线部署、MCP、时延和资源优化 | 满足复赛运行并争取时效性分数 | 全程有最小版本，后期集中优化 |
| 8 | 技术报告、演示和实验论证 | 复赛专家项共 30 分，证明方案可信 | 从中期开始并行，后期定稿 |

优先级 1—4 是初赛主线，优先级 5—8 是复赛竞争力主线。优先级不是“做完一个再开始下一个”：数据集、最小基线、合规接口和文档应并行推进；算法优化则按上述依赖关系推进。

## 三、优先级 0：先冻结规则、接口和禁止事项

### 要做的事情

建立一份 B01 内部规格说明，至少固定：

- 三个任务的输入字段和输出字段；
- `traj_result.jsonl` 的实际 JSON 结构和编码检查方式；
- 轨迹编号、样本编号、候选文本编号的命名规则；
- 主模型必须使用国内开放权重、支持本地离线部署；
- 专用模型基础模型总参数量不超过 4B，最多 2 个；
- 禁止闭源商业模型、在线服务、测试样例答案映射表和人工修改测试答案；
- 哪些步骤可以使用确定性工具：数据解析、几何/时序计算、检索索引、格式校验等。

### 为什么放在最前面

B01 对模型参数规模、部署方式和答案生成过程有明确限制。若先用在线大模型或不符合参数口径的模型做出原型，后续迁移到本地模型时可能需要重做数据、提示词、工具接口和评测流程。

### 完成标准

给定一条样例输入，程序能够在离线环境中完成解析、调用本地模型、生成一条合法 JSONL 结果，并通过字段、编码和格式校验。

## 四、优先级 1：建立自建数据集和评测基准

这是 B01 最应该提前投入的工作。官方不提供训练数据，数据建设本身就是赛题的一部分。

### 1. 先定义标签体系

建议先定义三层标签：

- **动作层**：转向、加速、减速、悬停、绕行、规避、巡检等；
- **轨迹片段层**：动作起止时间、持续时间、速度/方向变化、空间区域；
- **意图层**：巡检、接近、穿越、规避、徘徊、撤离等任务或意图。

标签体系要避免只写自然语言结论，还要保留可计算的轨迹证据，例如转向角、速度变化、停留时长、航迹形状和区域关系。

### 2. 构造数据来源

建议组合三类数据：

1. **规则可控的合成轨迹**：用于覆盖行为组合、噪声、采样间隔、缺失点和异常点；
2. **公开或自有的非敏感轨迹数据**：用于增加运动模式多样性；
3. **模型辅助生成的文本描述**：生成多种表达方式，再由人工抽检和程序校验。

合成数据可以使用几何和时序算法，但最终语义标签和文本描述需要经过一致性校验，避免文本与轨迹事实不一致。

### 3. 同时构造三种评测集

- 单模态分类/问答集：测行为识别准确率；
- 查询—轨迹检索集：测 Recall@5、nDCG@10；
- 轨迹—候选文本联合分析集：提前为复赛准备 F1、BERTScore、FActScore 风格评测。

评测集必须按场景、行为组合和文本表达划分，不能随机切分到导致训练集和测试集高度相似。至少保留一组“新组合”和“新措辞”作为泛化验证。

### 完成标准

团队能够在本地对任意模型输出计算：

- 单模态准确率；
- Recall@5、Recall@10、nDCG@10；
- 联合分析答案的字段级正确率和证据一致性；
- 平均响应时延。

没有这套评测基准，后续模型调优只能依赖主观样例，无法判断是否真正进步。

## 五、优先级 2：先做最小可运行端到端基线

### 推荐的最小闭环

```text
输入解析
  → 轨迹确定性特征计算
  → 本地开放权重模型
  → 结构化答案解析
  → JSONL 输出
  → 本地评测脚本
```

第一版不追求复杂 Agent，也不追求所有任务都高分，只解决以下问题：

- 输入能稳定解析；
- 轨迹时间序列和空间字段能转成模型可读表示；
- 模型能够输出合法、可校验的结果；
- 错误能够定位到解析、特征、检索、模型或输出格式；
- 同一套程序可以替换模型和提示词进行对比。

### 为什么要尽早做

B01 的最终交付是部署包，不是离线实验表格。最小闭环能够尽早暴露模型上下文长度、响应时间、JSON 生成、显存和依赖版本问题。它还可以作为后续所有改进的统一评测入口。

---

## 六、优先级 3：先解决单模态航迹语义理解

### 任务范围

先只处理航迹自身的行为和运动语义，不急于解释复杂文本意图。重点覆盖：

- 突发转向；
- 加速和减速；
- 悬停；
- 绕行和规避；
- 周期性巡检；
- 局部动作与整体运动意图的组合。

### 建议技术路线

采用“确定性轨迹工具 + 模型语义判定”的结构：

1. 工具计算速度、加速度、方向变化、曲率、停留时间、周期性和区域关系；
2. 将这些特征和必要的原始轨迹片段交给本地模型；
3. 模型负责把特征组合成行为语义，输出结构化答案和依据；
4. 使用规则做格式校验、数值范围校验和结果一致性检查，但不把固定规则当成最终语义判定器。

这符合题目允许使用确定性几何/时序计算，同时保持语义判定由模型完成的要求。

### 阶段目标

先获得可靠的单模态准确率，再扩展到多行为、多目标和有噪声轨迹。因为单模态表征会直接成为跨模态检索的索引内容和联合分析的证据。

---

## 七、优先级 4：重点攻克跨模态数据对齐关联

跨模态对齐是初赛最高分项，共 60 分，因此在单模态基线可用后，应将最多的算法优化资源投入这里。

### 推荐的分层方案

1. **轨迹侧表征**：使用轨迹工具提取运动事件、时空范围、持续时间和目标行为摘要；
2. **文本侧表征**：对查询和背景文本做语义分段，区分行为、任务、区域、时间和目标属性；
3. **共享检索空间**：建立轨迹摘要—文本描述的向量索引；
4. **混合召回**：向量召回结合结构化字段过滤和时间/区域约束；
5. **重排序**：使用本地模型对候选轨迹与查询文本做语义匹配，输出排序结果；
6. **指标优化**：直接围绕 Recall@5 和 nDCG@10 做负样本构造、候选数量和重排序实验。

### 为什么不能只做向量相似度

文本可能描述任务意图，轨迹则体现运动事实。仅靠表面相似度容易把“经过同一区域”误判为“执行同一任务”，也容易忽略时间顺序、方向和持续时间。结构化轨迹证据和模型重排序是提高排序质量的关键。

### 阶段目标

先稳定 Recall@5，再优化 nDCG@10。因为 Recall 解决“正确目标是否进入候选集”，nDCG 解决“正确目标是否排在前面”，二者需要分别设计召回和排序实验。

---

## 八、优先级 5：建设轨迹工具和 Agent 编排层

### 工具优先级

建议先做少量高价值工具，而不是一开始堆很多 MCP 工具：

1. 轨迹清洗和采样工具；
2. 速度、方向、加速度、曲率和停留检测工具；
3. 区域和时间关系查询工具；
4. 轨迹摘要生成工具；
5. 语义检索和候选重排序工具；
6. 证据引用和答案校验工具。

### Agent 的职责边界

- Agent 负责决定调用哪些工具、组合哪些证据、选择最终答案；
- 工具负责稳定计算，不负责用硬编码规则直接替代语义判断；
- 输出层负责把自然语言或模型自由文本转换为符合 JSONL 的结构化结果。

这比让大模型直接阅读超长原始轨迹更容易控制上下文、降低时延、提高可解释性。

---

## 九、优先级 6：复赛再重点开发多模态联合分析

多模态联合分析在初赛不计分，但复赛占 30 分，是复赛机器评分中最高的单项之一。它应在初赛两项能力稳定后集中开发。

### 要解决的具体问题

给定一条目标航迹、10 条候选文本和文本指令，输出：

- 目标可能执行的任务或意图；
- 选择该判断的相关文本；
- 与航迹事实一致的推理依据。

### 研发重点

- 候选文本排序和证据选择；
- 轨迹行为到任务意图的组合推断；
- 依据必须来自输入文本和轨迹事实，减少无依据扩写；
- 让输出可被 F1、BERTScore 和 FActScore 评价；
- 对结论、依据、引用候选文本分别做结构化输出。

### 不建议过早投入的内容

不建议在初赛主线尚未稳定时，先做图像、视频、电磁信号等额外模态。材料把这些列为技术方案加分方向，核心算法评测仍以航迹和文本为主。过早扩展会分散数据标注、模型调优和评测资源。

---

## 十、优先级 7：部署、时延和资源优化

部署工作要分成“最小版本早做”和“集中优化后做”两部分。

### 早期必须完成

- Linux 环境和 Python/PyTorch 版本固定；
- 本地开放权重模型加载；
- Docker 或等效可复现环境；
- JSONL 输入输出校验；
- 无外网运行检查；
- 显存、内存、磁盘和单样本响应时间记录。

### 后期集中优化

- 模型量化和推理批处理；
- 轨迹特征缓存和向量索引缓存；
- 减少不必要的 Agent 循环和工具调用；
- 控制上下文长度和候选数量；
- 并行处理相互独立的样本；
- 为复赛时效性测试建立固定基准。

B01 复赛时效性有 10 分，不能等到最后才发现系统虽然准确但响应过慢。

## 十一、优先级 8：技术报告、演示和合规证据

这项工作不应拖到提交前一周才开始。建议从中期开始持续记录：

- 每个版本的模型、数据、提示词、工具和评测结果；
- 单模态、跨模态和联合分析的消融实验；
- 规则工具与模型语义判定的边界；
- 本地部署、参数规模和离线运行证据；
- 错误案例、失败原因和改进前后对比；
- Agent 调用链、MCP 工具和输出校验流程。

复赛专家项共 40 分中的 30 分来自技术方案和智能体演示，报告与代码、实验结果不一致会削弱可信度。

## 十二、按比赛阶段安排资源

### 阶段 A：规则和基线期

目标：完成优先级 0—2。

主要产物：

- B01 内部接口和合规清单；
- 自建数据集第一版；
- 本地评测脚本；
- 可运行的 JSONL 基线；
- 初步单模态和检索结果。

### 阶段 B：初赛得分期

目标：完成优先级 3—4。

资源建议：

- 约 40% 投入单模态轨迹表征和行为识别；
- 约 50% 投入跨模态召回、排序和负样本构造；
- 约 10% 用于接口、部署和错误分析。

这个阶段不要因为 Demo 或额外模态而削弱初赛两项核心指标。

### 阶段 C：复赛能力扩展期

目标：完成优先级 5—8。

资源建议：

- 约 30% 投入多模态联合分析；
- 约 20% 投入检索和单模态继续优化；
- 约 20% 投入时延、部署和资源优化；
- 约 20% 投入技术报告、消融实验和演示；
- 约 10% 预留给官方新测试样本和接口变更。

比例可按团队人员特长调整，但复赛阶段不能只追求机器分数而忽略专家项。

---

## 十三、建议的团队分工

若团队规模允许，建议至少分成五个角色：

1. **数据与评测**：标签体系、轨迹合成、文本标注、数据切分、指标实现；
2. **轨迹理解**：时序特征、行为识别、轨迹摘要和异常处理；
3. **跨模态检索**：向量表征、召回、重排序、Recall/nDCG 优化；
4. **模型与 Agent**：本地模型适配、提示词、工具调用、证据生成；
5. **工程与交付**：Docker、MCP、资源监控、JSONL、报告和演示。

数据与评测角色应从第一天开始，因为它决定其他角色是否能快速判断改动是否有效。

---

## 十四、最终建议

B01 的合理主线是：

> 先固定合规边界 → 立即建设自有数据和评测 → 打通最小闭环 → 做好单模态航迹语义 → 集中优化跨模态检索排序 → 再补 Agent 工具化、联合分析、时延和演示。

如果只能先做三件事，应选择：

1. 建立可复用的轨迹—文本数据集和本地评测集；
2. 完成一个可离线运行、能输出合法 JSONL 的最小基线；
3. 围绕单模态准确率、Recall@5 和 nDCG@10 做可重复的实验迭代。

如果只能暂缓一项，应暂缓其他模态扩展和复杂 Demo，而不应暂缓数据集、评测脚本、合规部署和初赛两项核心任务。

## 补充：对 `B01赛题初赛数据集-stage1.rar` 的理解

根据当前 B01 PDF，不能把该文件名本身当作已在赛题说明中定义的正式数据集名称。PDF 明确说明“不提供训练数据”，同时说明初赛会使用主办方提供的标准测试集进行单模态语义理解和跨模态对齐关联评测。

因此，在尚未解压核对文件前，较稳妥的理解是：

1. `stage1.rar` 很可能是初赛阶段发放的测试/调试输入包，而不是带有公开答案的训练集；
2. 即使压缩包不包含 GT，主办方仍可能在后台保留 GT，用于计算 Accuracy、Recall@5 和 nDCG@10；
3. 参赛队不能依赖公开答案，必须让自建的离线 Agent 对每个样本生成结果；
4. 最终提交文件应为 `traj_result.jsonl`，每条记录至少包含“样本编号”和“结果”两个字段；
5. 初赛重点是前两项任务：单模态航迹语义理解、跨模态数据对齐关联。多模态联合分析属于复赛新增任务，除非官方对 stage1 另有说明。

需要注意：目前仅凭 PDF 和文件名，无法确认 `stage1.rar` 是否包含训练标签、样例 GT、验证集答案或多个任务的完整输入。解压后应重点检查文件名、JSON/CSV 字段、是否存在 label/answer/target 等字段，以及是否有单独的 README 或数据说明。

## 补充：根据官方测试样例确认的输入输出结构

用户提供的两张 B01 样例图比 PDF 文字描述更具体，可以确认至少存在以下两类 JSON 任务。

### 1. 单模态数据语义理解样例

输入结构可概括为：

```json
{
  "样本编号": "seg_000001",
  "航迹数据": {
    "航迹编号": "traj_000001",
    "起始时间": "2025-05-01T12:00:00Z",
    "点位序列": [
      {
        "时间戳": 10,
        "经度": 116.3912,
        "纬度": 39.9075,
        "高度": 3200,
        "速度": 230
      }
    ]
  },
  "文本指令": "以下哪种高度分段序列最符合该航迹？A...B...C...D..."
}
```

截图中为了展示格式只保留了一个时间节点，真实样本应包含完整点位序列。题目要求模型根据高度随时间的变化，从多个选项中选择最符合航迹的分段序列；答案示例为：

```json
{
  "样本编号": "seg_000001",
  "结果": "A"
}
```

#### 对系统设计的直接影响

- 这是**多选项语义判定**，不是让模型自由生成一段解释文字；
- 应先对点位序列计算高度变化段，再由模型或受约束的语义模块完成选项判定；
- 输出层必须把答案规范化为选项字符串，例如 `A`，避免输出“答案是 A，因为……”导致格式或准确率问题；
- 评测会重点考察行为/轨迹模式识别准确率，轨迹预处理和分段质量会直接影响结果；
- 这类任务可以建立“轨迹数值特征 → 行为分段 → 选项判定”的工具链，而不应把完整长轨迹直接原样塞给大模型。

### 2. 跨模态数据对齐关联样例

输入结构可概括为：

```json
{
  "样本编号": "retrieval_000001",
  "区域": [
    {
      "区域编号": "区域 A",
      "类型": "多边形",
      "坐标": [
        [116.2800, 39.8200],
        [116.3600, 39.8200],
        [116.3600, 39.9000],
        [116.2800, 39.9000]
      ]
    }
  ],
  "文本指令": "查询上午8点至10点进入区域A，离开后持续朝西北方向飞行的航迹。",
  "top_k": 10
}
```

答案示例是一个有顺序的航迹列表：

```json
{
  "样本编号": "retrieval_000001",
  "结果": [
    {"序号": 1, "航迹编号": "traj_000137"},
    {"序号": 2, "航迹编号": "traj_000142"}
  ]
}
```

截图中完整示例列出了 1 至 10 名航迹，因此 `top_k: 10` 表示需要返回最多 10 条按相关性排序的结果。

#### 对系统设计的直接影响

- 这是**带排序的跨模态检索任务**，不是简单判断“相关/不相关”；
- 查询同时包含时间约束、空间约束、进入/离开事件和离开后的方向约束；
- 必须使用区域多边形判断、时间窗口过滤、轨迹方向计算等确定性工具；
- 之后还需要根据文本语义和轨迹行为对候选航迹排序；
- 初赛的 Recall@5 和 nDCG@10 意味着前 5 名召回正确目标很重要，同时 1—10 名的排序质量也会影响分数；
- 输出中的 `序号` 和 `航迹编号` 应严格保持顺序、唯一性和格式一致。

### 3. 对“stage1 是否不带 GT”的进一步判断

这两张图展示的是“验证逻辑的样例输入、输出样本”，不是 stage1 压缩包本身的目录清单。它们可以确认：

- 测试输入是问题样本，Agent 需要根据样本生成结果；
- 单模态答案可能是选项标签；
- 跨模态答案是有序的 Top-K 航迹编号列表；
- 真实测试集的正确答案不应随输入一起提供，否则无法进行公平排名。

所以更准确的表述是：stage1 很可能是**不公开 GT 的初赛输入/测试数据包**；主办方在评测端保留 GT，参赛队提交 Agent 生成的结构化答案。最终仍需解压 stage1 检查是否附带训练样例、开发集标签或 README，不能仅凭截图断言压缩包内部完全没有任何标签。

### 4. Agent 的最小处理架构

```text
JSON 输入
  ├─ 单模态样本：轨迹解析 → 高度/速度/方向分段 → 选项判定 → 输出 A/B/C/D
  └─ 检索样本：区域/时间/方向约束计算 → 候选召回 → 语义重排序 → 输出 Top-K 航迹编号
        ↓
严格 JSON 结构校验
        ↓
traj_result.jsonl
```

这说明 B01 初赛的第一版系统不必从“通用聊天 Agent”开始，而应优先实现两个可验证的任务管线：轨迹事件识别和带时空约束的排序检索。
