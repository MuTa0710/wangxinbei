## 二、B01：多模态数据语义理解

### 1. 赛题究竟要做什么

B01 的主线是把“目标航迹”与“文本”放进同一语义理解流程，完成从低层运动数据到高层任务/意图的推断。材料明确将任务分成三个层次：

1. **单模态数据语义理解**：读取目标航迹序列，识别突发转向、加速/减速、悬停、绕行、规避、周期性巡检等行为模式，同时理解局部动作和整体运动意图。
2. **跨模态数据对齐关联**：把查询文本和航迹库对齐到共享语义空间，根据自然语言指令找出相关的航迹编号序列。
3. **多模态数据联合分析**：联合航迹和 10 条候选文本，推断目标可能执行的任务或意图，并给出可解释的依据。

因此，它不是简单的轨迹分类，也不是单纯的文本问答，而是一个“轨迹时序理解 + 文本检索/对齐 + 证据化推理”的智能体系统。

### 2. 输入和输出

| 子任务 | 输入 | 输出 |
|---|---|---|
| 单模态语义理解 | 目标航迹序列、文本指令、必要区域信息 | 正确答案 |
| 跨模态对齐关联 | 查询文本、目标航迹库、必要区域信息 | 航迹编号序列 |
| 多模态联合分析 | 目标航迹序列、10 条候选文本、文本指令 | 目标可能执行的任务/意图，以及推断依据 |

初赛只评测前两项；复赛加入第三项。

### 3. 数据和训练准备

- 赛题**不提供训练数据**。
- 参赛队需要依据任务样例，自行搜集、清洗、标注数据并决定训练集格式。
- 样例输入/输出用于理解验证逻辑，但不能把测试样例答案硬编码进程序。
- 这意味着前期工作不只是模型开发，还包括行为模式定义、轨迹数据构造、文本描述和意图标签设计、正负检索样本构造等。

### 4. 模型与部署约束

- 技术路线不限，但核心求解必须依靠基础模型或学习算法。
- 鼓励使用智能体、大语言模型、多模态模型、检索增强和工具调用。
- 不能主要依靠人工规则、固定阈值、关键词匹配、手工事件—意图表或针对测试样例的模板。
- 推理主模型必须是**国内开放权重模型**，能够在复赛环境本地私有化部署。
- 面向任务的专用模型：基础模型总参数量不超过 4B，最多 2 个；鼓励多个任务共享模型。
- MoE 按总参数量计算；LoRA 等适配器参数计入总量；量化不会改变参数规模认定。
- 复赛每队最低环境：显存不低于 64GB、支持 FP16/BF16 的 GPU，CPU 不低于 32 核，内存不低于 128GB，固态存储不低于 512GB。
- 要求离线完整部署和运行。

### 5. 提交和交付

- 结果文件：traj_result.jsonl。
- UTF-8 编码；每条记录对应一个测试样本，包含“样本编号”和“结果”两个字段。
- 交付智能体部署包、符合 MCP 协议的专用工具、源代码、说明文档和技术报告。
- 技术报告需要覆盖系统设计、关键技术和实验结果分析。
- 初赛 A 榜每天最多提交 3 次；B 榜开放后允许提交 3 次；复赛允许提交 3 次。

### 6. 评分重点

**初赛 100 分，全部机器评测：**

- 单模态数据语义理解：准确率，40 分；
- 跨模态数据对齐关联：Recall@5 占 40%，nDCG@10 占 60%，共 60 分。

**复赛 100 分：**

- 单模态语义理解：10 分；
- 跨模态对齐关联：20 分，Recall@10 和 nDCG@10；
- 多模态联合分析：30 分，相关文本、研判结论和研判依据分别使用 F1、BERTScore、FActScore；
- 技术方案：20 分，专家评审；
- 智能体演示：10 分，专家评审；
- 时效性：10 分，按主办方输入问题到得到答案的平均时间排序。

### 7. 这道题实际考验什么

- **数据建设能力**：没有官方训练集，需要自己构造轨迹行为和文本语义样本。
- **模型能力**：轨迹不是天然语言，需要时序编码、特征抽取或轨迹专用工具。
- **检索能力**：跨模态关联有明确 Recall 和 nDCG 指标，排序质量很重要。
- **推理可解释性**：复赛要求输出任务/意图及依据，并以 FActScore 等指标评价事实支撑。
- **工程能力**：本地模型、离线运行、MCP 工具、响应时延都影响结果。

### 8. 适合什么样的队伍

适合有大模型应用、RAG、向量检索、轨迹时序建模、自动标注和数据构造能力的队伍。若团队没有现成训练数据，前期数据生产成本会比较高；如果擅长搭建“主模型 + 轨迹分析工具 + 检索库 + 证据生成”的闭环，优势会比较明显。

## 三、B02：目标检测跟踪

### 1. 赛题究竟要做什么

B02 要构建一个雷达目标检测跟踪智能体，完成完整链路：

> 雷达点迹输入 → 杂波抑制 → 目标检测 → 点迹建航 → 航迹关联 → 航迹稳定维持 → 输出目标航迹

题目重点关注低慢小、高机动、强杂波、低信噪比和伴飞目标等场景。核心目标是“快速检测、稳定跟踪、多场景泛化”。

### 2. 输入和输出

**输入：雷达点迹数据。**字段包括：

- Time：时间，毫秒；
- Azimuth：方位角，0～1 归一化；
- Elevation：俯仰角，0～1 归一化；
- Distance：距离，0～1 归一化；
- Amp：幅度，0～1 归一化；
- SNR：信噪比，0～1 归一化；
- CircleID：圈号；
- PntID：点序号。

**输出：雷达航迹结果。**航迹字段包括时间、方位、俯仰、距离、BatchID、CircleID 和 PntID。

### 3. 最关键的实时交互约束

- 智能体必须通过标准接口与数据收发软件通信。
- 禁止直接读取测试集原始文件。
- 数据按“单圈”到达，智能体需要实时完成检测、跟踪和 ID 关联。
- 如果单圈规定时间内未返回，系统将该圈判定为漏检，并强制进入下一圈或终止测试。

这意味着离线批处理、预先读取完整测试集、依靠未来信息平滑轨迹等方法不符合交互设定。低延迟和稳定状态管理是任务的一部分。

### 4. 模型、软硬件和代码约束

- 可使用主办方“后羿”基础模型进行微调，也可使用开源或自研模型，但必须离线部署。
- 题目建议 NVIDIA 生态、RTX 40 系及以上显卡。
- 智能体包含模型权重、推理引擎及必要程序，必须在**不高于 24GB 显存**条件下完整部署和推理。
- 建议 Python 3.12、CUDA 12.8+、PyTorch 2.7+；其他语言需提供完整 Docker 环境。
- 推荐 Ubuntu 22.04 或 Windows 10。
- 程序包需包含 Dockerfile、run.sh、requirements.txt、README.md、src/ 等标准内容。

### 5. 数据特点

题目明确说明，所有目标、轨迹和杂波均为仿真的虚拟实体，地理环境也为统计仿真，不对应真实目标或真实地理坐标。材料给出的数据主要用于调试算法、验证逻辑和提供样例输入输出。

### 6. 提交与比赛流程

- 日常打榜：提交验证集航迹结果包，每日 2 次，每队最多 50 次；仅用于参考，不直接作为初赛晋级依据。
- 初赛：提交完整程序包，组委会在统一测试集运行，按客观评分排名，前 10 名晋级。
- 复赛：现场使用统一测试集运行智能体并提交结果；同时提交程序包、测试集跟踪结果包、技术报告和完整源代码，源代码用于合规审查。

### 7. 评分重点

B02 初赛和复赛以客观评分为主，客观评分占 100%；复赛答辩和代码审查是排名确认环节，不单独计分。

| 指标 | 权重 | 实际含义 |
|---|---:|---|
| 空情掌握率 | 30% | 输出航迹点与真值航迹点的匹配程度 |
| 虚警率得分 | 10% | 未匹配真值的输出点越少越好 |
| 航迹零碎度 | 20% | 同一真值航迹被切成多个输出批次的程度 |
| 起批及时性 | 20% | 是否尽早建立航迹；第三点起批，超过 50 秒基本不得分 |
| 最大连续跟踪时长 | 20% | 最长连续输出航迹覆盖真值航迹的程度 |

同分时依次比较：空情掌握率、最大连续跟踪时长、航迹零碎度、起批及时性、虚警率。

### 8. 这道题实际考验什么

- **流式算法**：每圈处理、超时控制和状态维护。
- **经典雷达跟踪能力**：检测、数据关联、起批、航迹维持、断批处理。
- **弱目标和高机动鲁棒性**：不能只在平稳目标上表现好。
- **工程优化**：显存上限 24GB，且有实时响应约束。
- **评测目标明确**：五项指标和权重公开，便于围绕指标优化。

### 9. 适合什么样的队伍

适合有雷达信号处理、目标跟踪、数据关联、实时系统和 GPU 推理优化经验的队伍。若团队主要优势是大语言模型应用，而缺少流式雷达跟踪经验，直接参赛的学习成本会高于 B01；但如果已有成熟航迹算法，B02 的评测闭环较清晰，投入产出关系更容易测量。

## 四、B04：目标本体表征与多源数据融合

### 1. 赛题究竟要做什么

B04 面向复杂电磁感知场景，把不同平台、不同传感器产生的电磁数据和场景文本统一表示，形成可信的电磁目标态势。具体工作可以拆成五步：

1. 对 A 类传感器脉冲数据进行局部分组/聚类；
2. 预测目标类别和工作状态；
3. 将不同 A 类平台的局部对象融合成统一 object_id；
4. 将统一对象与 B 类传感器航迹进行跨源关联；
5. 用本体模型、关系模型和证据组织方式形成可查询、可追溯的态势表达，复赛还要输出态势报告。

它的核心不是单一分类器，而是“局部聚类 + 属性识别 + 跨平台实体解析 + A-B 航迹关联 + 本体化表达”的组合任务。

### 2. 输入数据

**A 类传感器训练数据：**

scenario_id、data_version、pulse_id、datetime、toa、三个隐藏参数 param1/2/3、doa、传感器经纬度和高度、platform_id、训练标签 target_id、target_class、target_state。

**B 类传感器训练数据：**

scenario_id、data_version、track_id、时间、目标经纬度、高度、target_type（例如大/中/小 RCS）、可能公开的 target_class、训练标签 target_id。

训练数据还配套场景背景、目标行为特点等文本资料。

**测试阶段缺失信息：**

- A 类测试数据删除 target_id、target_class、target_state；
- B 类测试数据删除 target_id；
- B 类测试数据既可能有与 A 类对象对应的航迹，也可能有只被 B 类传感器观测到的目标。

### 3. 输出文件和硬性规则

#### pulse_predictions.csv

字段：

scenario_id、data_version、pulse_id、local_cluster_id、object_id、target_class、target_state。

规则：

- 每个输入 pulse_id 必须出现且只能出现一次；
- 同一 platform_id 内，local_cluster_id 表示一个局部对象；
- object_id 表示跨平台融合后的统一对象；
- target_class、target_state 可以为空，表示未预测；
- 编号可自行定义，评分器按对象成员关系评价。

#### object_track_links.csv

字段：

scenario_id、data_version、object_id、track_id、link_status。

规则：

- link_status 只能是 matched 或 no_match；
- matched 必须填写输入中存在的 B 类 track_id；
- 一个 B 类航迹不能同时关联多个 object_id；
- no_match 时 track_id 为空；
- 不能通过删除对象或删除脉冲来表示未关联。

### 4. 交付物和运行约束

- 建议 Python；其他语言需要提供完整 Docker 环境。
- 代码包必须含 Dockerfile、run.sh、requirements.txt、README.md、output/ 等目录或文件。
- 初赛输出两个 CSV，并提交本体建模方案、理论模型和智能体模型。
- 复赛还要提交源码、技术实现说明、态势报告、技术总结报告和演示视频/Demo。
- 材料未限定固定开源框架版本和固定运行环境，但必须能在 Docker 中运行。

### 5. 评分重点

机器评分覆盖五个方向：

- 聚类识别准确率；
- 类型识别准确率；
- 状态识别准确率；
- 跨平台融合准确率；
- A-B 跨源关联准确率。

总分：

- 初赛：0.8 × 机器评分 + 0.2 × 专家评分；
- 复赛：0.6 × 机器评分 + 0.4 × 专家评分，并结合时效性。

专家评分关注技术方案的合理性、创新性、完整性、可实现性和应用价值。

### 6. 这道题实际考验什么

- **聚类与识别的联合优化**：局部对象划分错误会影响后续所有指标。
- **实体解析和跨平台融合**：同一目标在不同平台上的观测需要统一编号。
- **跨源关联**：A 类脉冲对象与 B 类航迹并非一一显式对应，且存在 B-only 目标。
- **本体和关系建模**：不能只给出 CSV，还需要说明对象、属性、状态、证据和关系如何表达。
- **结果可追溯性**：复赛态势报告要解释“为什么认为这些数据属于同一个目标”。

### 7. 适合什么样的队伍

适合有时序/信号数据聚类、实体对齐、知识图谱或本体建模、数据工程和可解释分析经验的队伍。它的训练数据和字段定义比 B01 更明确，输出格式也更结构化；但任务链条长，任何一个环节的错误都会传导到后续融合和关联指标。

## 五、“反思式决策”赛题

### 1. 赛题究竟要做什么

这道题不是单一模型分类，而是要构建一个能够在红蓝对抗中不断复盘和改进的 AI 指挥决策系统。赛题将任务拆成三个子任务：

#### 子任务 1：红蓝高对抗指挥决策场景设计

自行设计一套高对抗、高复杂的场景，例如反无人机、无人蜂群对抗、多目标火力打击。

约束：

- 符合军事基本逻辑和物理规律；
- 装备参数、性能指标来自公开资料或合理假设；
- 不得使用涉密数据；
- 不能直接复制或简单修改主办方基线场景。

交付：1 套红蓝对抗场景、1 篇场景描述报告、1 份配套数据。

#### 子任务 2：指挥决策智能体反思演进

先提供基线指挥决策智能体，再设计反思演进机制，使智能体在面对新场景时，在有限交互轮次内显著优化策略。可采用或组合：

- 基于知识的反思；
- 基于梯度的反思；
- 基于模型的反思。

输入是主办方红蓝对抗场景数据，输出是决策智能体运行结果。

#### 子任务 3：反思知识自主构建与演进

把一次次对战后的零散反思经验沉淀成可复用知识：

1. 从反思结论中抽取关键要素和因果关系；
2. 使用知识图谱、概率图模型、可微逻辑网络或动态本体建模；
3. 支持知识库增量更新、冲突检测和冲突消解；
4. 后续决策主动查询并使用知识库，支持跨场景演进。

### 2. 场景和数据结构

主办方提供 1 套基线红蓝对抗场景，参赛者自行设计 1 套场景。

基线场景采用反无人机集群形式，可用 {T, W, P, V} 描述：

- T：蓝方目标无人机集合；
- W：红方反无人武器集合；
- P=[pij]：武器对目标的毁伤概率矩阵；
- V=[vj]：目标价值向量。

初赛使用主办方基线场景，设置 20×50 和 200×500 两种规模，并加入无人机数量突增、反无设备被毁、对抗干扰、有无人混合突防、无人机性能突变等变化。复赛使用主办方基线场景加 4 套优选参赛场景，共 5 套场景，每套 10 个标准测试用例。

### 3. 输入输出和运行规范

- 输入文件为 JSON，放在容器 /input 目录；文件名形如 scene.json。
- 输出文件为 JSON，放在 /output 目录。
- 程序需要分别生成关闭反思功能的 norethink 结果和开启反思功能的 rethink 结果。
- 输出文件名需与输入文件一致。
- 配置文件必须支持大模型 API 的 api_key、base_url、model 三个核心参数，并可配置 temperature、max_tokens 等。
- 可使用 Python、C++、Java 等主流语言；需用 Docker 部署。
- 可使用大赛指定开源预训练模型、公开领域词典和公开本体库；禁止外部私有业务数据，禁止人工修改测试集答案。

### 4. 评分重点

#### 初赛 100 分

| 评分项 | 分值 | 评测方式 |
|---|---:|---|
| 红蓝对抗场景设计 | 10 | 专家评审：新颖性、复杂性、合理性、需求贴合度 |
| 反思式决策解决方案 | 40 | 专家评审：反思机制创新性、多样性、收敛性、可解释性、知识抽取建模和知识驱动决策 |
| 智能体反思速度 | 25 | 机器评分，10 个标准测试用例按求解时间排名；超 10 分钟或排名最后可能不得分 |
| 智能体反思效果 | 25 | 机器评分，比较反思前后期望毁伤价值，并使用基线质量惩罚系数 |

#### 复赛 100 分

- 反思式决策解决方案：30 分，专家评审；
- 智能体反思速度：25 分，机器评分；
- 智能体反思效果：25 分，机器评分；
- 跨场景能力：20 分，在另外 4 套场景上测试，每个场景达到期望毁伤价值门限可得相应分值。

### 5. 交付物

初赛需提交：

1. 1 套自设计红蓝对抗场景、场景描述报告和配套数据；
2. 《反思式决策解决方案 V1.0》，不超过 50 页；
3. 不超过 1500 字的成果简介；
4. 两套算法并统一集成为反思式决策智能体：指挥决策智能体演进算法、反思知识自主构建与演进算法；
5. 代码、Dockerfile 和运行说明。

复赛需提交 V2.0 技术报告、答辩汇报片、两套算法及其镜像和运行说明，并参加封闭环境内场比测与现场答辩。

### 6. 这道题实际考验什么

- **场景建模能力**：要设计公平、复杂、可计算且不泄露敏感信息的对抗环境。
- **基线和增量改进能力**：评分不仅看反思后结果，还会根据反思前基线质量施加惩罚。
- **反思机制设计**：必须证明反思带来了速度和效果上的提升，而不是只做一次性规划。
- **知识工程**：反思结论要结构化、可查询、可更新、可冲突消解。
- **泛化能力**：复赛新增 4 套参赛场景，不能只针对主办方基线调参。
- **解释和答辩能力**：专家评分占比高，技术报告必须和代码、实验结果一致。

### 7. 适合什么样的队伍

适合有多智能体/强化学习/组合优化、大模型 Agent、知识图谱、概率建模和仿真环境开发经验的队伍。它的开放度最高，方案创新空间大，但评测不只是代码分数，还包含场景设计和技术方案评审，项目管理和答辩准备工作量也最大。

## 六、横向对比：选择时最有用的事实

### 1. 任务边界和数据准备

| 维度 | B01 | B02 | B04 | 反思式决策 |
|---|---|---|---|---|

| 官方训练数据 | 不提供 | 主要提供调试/样例数据 | 提供训练数据和文本资料 | 提供基线场景；另需自建场景 |
| 是否需要自建训练集 | 是，明确要求 | 材料未要求自建训练集 | 可基于官方训练数据开发 | 重点是自建对抗场景和知识积累 |
| 是否要求实时 | 有时效性评分 | 强制逐圈实时 | 复赛结合时效性 | 反思速度是 25 分 |

### 2. 评分确定性和专家因素

| 赛题 | 机器评分情况 | 专家评分情况 | 选择含义 |
|---|---|---|---|
| B01 | 初赛 100% 机器；复赛机器 60% | 复赛技术方案 20 分、演示 10 分、时效性 10 分 | 先靠算法进入竞争，再靠方案和工程展示拉开差距 |
| B02 | 初赛、复赛客观评分占 100% | 答辩和代码审查不单独计分 | 指标最明确，工程性能决定性强 |
| B04 | 初赛机器 80%，复赛机器 60% | 初赛 20%，复赛 40% | 本体方案、报告和可解释性在复赛更重要 |
| 反思式决策 | 初赛机器 50%，复赛机器 70% | 初赛专家 50%，复赛方案专家 30% | 创意、场景和技术论证影响很大 |

### 3. 资源约束差异

- **B01**：复赛最低 64GB 显存、32 核 CPU、128GB 内存、512GB 存储；模型必须是国内开放权重并可本地部署。
- **B02**：完整系统不高于 24GB 显存，且必须满足逐圈实时接口。
- **B04**：材料未给出固定显存上限和固定框架版本，但必须 Docker 化并输出标准 CSV。
- **反思式决策**：允许大赛指定开源模型和 Docker，核心限制更多来自场景规模、反思耗时、输出接口和合规要求。

### 4. 交付复杂度

从交付内容看，复杂度大致如下：

1. **B02**：程序包 + 航迹结果，主要是在线系统工程；
2. **B04**：程序/结果 + 本体建模方案，复赛增加态势报告、技术说明、总结和演示；
3. **B01**：部署包、MCP 工具、源代码、报告，还要自建训练数据和处理多任务语义输出；
4. **反思式决策**：自建场景、两套算法、两种运行模式、技术报告、成果简介、答辩片、Docker 镜像，综合交付最复杂。

这里的“复杂度”是按材料列出的工作面估计，不等同于最终获奖难度。

## 七、按团队能力选择：事实对应关系

### 如果团队已有雷达跟踪/信号处理基础

优先考察 **B02** 或 **B04**：

- B02 目标最集中，输入输出单一，评分指标公开且完全客观；
- B04 需要进一步具备多源数据对齐、本体和知识表达能力，但官方训练字段和标签更完整，能把已有信号处理能力扩展到融合任务。

### 如果团队已有大模型、RAG、Agent 和文本处理基础

优先考察 **B01** 或 **反思式决策**：

- B01 的任务结构清楚，适合做轨迹工具、检索、语义判定和证据生成的工程闭环；
- 反思式决策的创新空间更大，但必须补足仿真、组合优化、反思评价、知识库和跨场景测试能力。

### 如果团队训练数据和标注能力有限

- B01 的官方不提供训练集，是明确的额外成本；
- B04 有训练数据、字段说明和文本资料，数据启动成本相对可控；
- B02 更依赖算法和工程调试，是否适合取决于团队的雷达数据经验；
- 反思式决策的主办方基线可用于启动，但自设计场景和知识演进仍需要较强建模能力。

### 如果团队希望减少专家评分不确定性

优先看 **B02**。它的初赛、复赛客观评分占 100%，而且五项指标与权重都公开。B01、B04 和反思式决策都在复赛或初赛中包含技术方案、演示、场景或知识建模的专家评价。

### 如果团队希望通过方案创新获得额外空间

优先看 **反思式决策** 或 **B04**：

- 反思式决策可以在场景设计、反思机制、知识抽取和跨场景迁移上形成差异化；
- B04 可以在本体设计、证据组织、图谱表达、跨源融合和态势报告上形成差异化。

### 如果团队硬件资源有限

- B02 的显存上限最严格，要求完整系统不超过 24GB；
- B01 复赛主办方提供较高配置，但初赛需要自行解决算力；
- B04 的材料没有明确显存上限，部署自由度较大；
- 反思式决策需要根据大模型和场景规模评估运行时间，不能只看显存。

## 九、结论性判断

从“具体要做什么”看：

- **B01** 是多模态语义理解和检索推理题，最大额外工作是自行建设训练数据；
- **B02** 是实时雷达检测跟踪题，最大约束是逐圈在线处理和 24GB 显存上限；
- **B04** 是多源电磁数据融合题，最大工作量是聚类、跨平台对象统一、A-B 关联和本体化态势表达的完整链路；
- **反思式决策** 是“场景设计 + 反思进化 + 知识自主构建 + 跨场景验证”的系统型题目，开放性和交付复杂度最高。

如果只根据当前材料进行初步筛选：

1. 追求评测目标清晰、专家因素少：优先研究 **B02**；
2. 希望利用已有训练数据、做多源融合和知识表达：优先研究 **B04**；
3. 具备大模型应用和数据构造能力、希望做语义智能体：优先研究 **B01**；
4. 具备较强系统研发和创新方案能力、能承担最大交付量：考虑 **反思式决策**。

最终选择应以团队现有能力与上述任务的匹配度为准，而不应只按题目名称判断难度。
