# B01 具体落地实施方案

## 1. 方案目标

本方案把已有的调研、stage1 数据 EDA 和总体路线转成可以在当前 Docker 环境中逐步实现的工程方案。

首版目标不是构建一个通用聊天 Agent，而是完成两个可评测、可追踪、可离线运行的任务管线：

1. **task1 航迹理解**：根据航迹点序列和题目选项，输出一个选项字母；
2. **task2 跨模态检索**：根据自然语言、时间、区域和行为条件，从 2,000 条航迹中输出有序 Top-K 航迹编号。

系统采用以下分工：

> 确定性模块计算时间、距离、方向、区域交互和行为事实；本地 Qwen3 负责中文题意解析、选项语义理解和结构化查询生成；输出模块负责严格生成官方 JSONL。

首版先保证可解释、可调试和格式正确，再增加向量检索、重排序和自监督表征。

## 2. 已冻结的事实和约束

### 2.1 数据规模

| 数据 | 规模 | 工程影响 |
|---|---:|---|
| task1 分段理解 | 50 条 | 适合做开发集和错误分析，不适合直接微调大模型 |
| task1 区域理解 | 50 条 | 需要多边形事件引擎和时间换算 |
| task2 查询 | 50 条 | 查询包含时间、区域、否定和行为顺序组合 |
| task2 航迹库 | 2,000 条、483,657 个点 | 可以离线完整预计算，不必一开始引入向量数据库 |

官方 README 明确指出：task2 航迹点不保证按时间递增，使用前必须排序；坐标顺序为 `[经度, 纬度]`；高度单位为米，速度单位为 `m/s`。

### 2.2 提交格式

所有任务结果合并到一个 `traj_result.jsonl`，每行一个 JSON 对象，`样本编号` 不得重复或遗漏。

- task1：官方 README 要求使用 `选项` 字段，例如 `{"样本编号":"seg_000001","选项":"A"}`；
- task2：使用 `结果` 字段，值为带 `序号` 和 `航迹编号` 的有序列表。

当前目录中的提交示例对 task1 使用了 `结果` 占位字段，与 README 不一致。因此输出层必须做成可配置的 schema adapter：默认以 README 的 `选项` 为准，同时保留切换开关，最终提交前以赛事官方最新通知为准，不能把字段名散落在业务代码中。

### 2.3 环境

当前容器已经验证：Ubuntu 20.04、Python 3.12.10、PyTorch 2.3.0+cu121、Transformers 4.51.3，并能通过 `--gpus all` 使用 RTX 4090。

主语义模型先选 **Qwen3-4B**；开发阶段可用 Qwen3-1.7B 作为快速回归模型。首版只启用一个主模型，不同时引入多个专用模型，降低参数口径和部署风险。

## 4. 统一数据契约

### 4.1 标准轨迹对象

所有 task1 和 task2 轨迹先转换成统一对象：

```text
Trajectory
  trajectory_id: str
  start_time_utc: datetime
  points: list[Point]
  quality: QualityFlags

Point
  timestamp_utc: datetime
  relative_seconds: float | None
  longitude: float
  latitude: float
  altitude_m: float
  speed_mps: float
  heading_deg: float | None
```

task1 的 `时间戳` 是相对于起始时间的秒数；task2 的 `时间戳` 是 UTC ISO 8601 字符串。两者在进入算法层后都转换为 UTC 时间和相对秒数，避免不同任务混用时间语义。

### 4.2 派生特征对象

相邻点和固定窗口计算：

- `dt_seconds`；
- 水平距离、三维距离；
- 位置推导航向；
- 航向环绕差分；
- 速度变化、加速度；
- 高度变化率；
- 转向率、局部曲率；
- 直线拟合误差；
- 局部位移比；
- 盘旋/绕飞候选分数；
- 时间跳变、重复点、异常点标记。

原始值不覆盖。负高度、零速度、高速点、重复时间和大时间间隔全部保留，并记录质量标记，避免误删可能对应真实题意的阶段。

### 4.3 区域事件对象

每条轨迹与每个多边形区域生成：

```text
RegionEventSummary
  region_id
  start_inside
  end_inside
  entry_events: [{time, interpolated, source_segment}]
  exit_events: [{time, interpolated, source_segment}]
  dwell_intervals: [{start, end, duration}]
  outside_to_inside_count
  total_dwell_seconds
  event_order
```

事件状态机固定为：

```text
outside -> inside：记录进入
inside  -> outside：记录离开
inside  -> inside：累计停留
outside -> outside：无事件
```

起点在区域内不计为一次“从区外进入”。跨边界时间使用相邻点线性插值，并为边界点、切线、重复进入设置容差和明确规则。

### 4.4 task2 查询 IR

Qwen3 不直接输出航迹编号，而是输出经过 schema 校验的查询中间表示：

```json
{
  "time": {"start": null, "end": null},
  "altitude_m": {"min": null, "max": null},
  "speed_mps": {"min": null, "max": null},
  "regions": {
    "must_intersect": [],
    "must_not_intersect": []
  },
  "behavior_sequence": [
    {"type": "", "order": 1, "max_gap_seconds": null}
  ],
  "top_k": 10
}
```

必须区分“没有区域条件”“必须经过区域”“不得经过区域”，不能把空区域列表解释为否定条件。非法 JSON 只允许一次自动修复；修复失败时记录错误并采用保守解析，不让 Agent 无限循环。

## 6. task1 落地方案

### 6.1 分段理解

#### 阶段 A：候选边界检测

先从高度、速度、加速度、航向变化、转向率和曲率生成窗口特征。候选边界由以下信号共同提出：

1. 高度变化方向或高度变化率显著改变；
2. 速度变化方向或加速度显著改变；
3. 航向变化/转向率显著改变；
4. 直线飞行与曲线/盘旋形态切换；
5. 采样间隔变化仅作为质量信号，不直接作为行为标签。

第一版不训练复杂端到端分段网络，而是先得到候选片段，确保每个候选片段能解释。

#### 阶段 B：片段摘要

每个候选片段生成：

- 起止时间和持续时长；
- 高度、速度起点/终点/均值和变化方向；
- 航向变化总量；
- 曲率、转弯率和直线误差；
- 盘旋/绕飞分数；
- 数据质量标记。

#### 阶段 C：选项判别

模型输入优先使用“轨迹摘要 + 题目选项”，不直接发送全部原始点位。模型输出受约束 JSON：

```json
{"option":"A","evidence_segments":[0,1],"confidence":0.0}
```

最终只取 `option`，并限制为 `A/B/C/D`。确定性特征用于检查模型证据是否与轨迹事实冲突；不能通过样本编号或题目文本做答案映射。

#### 训练和验证

由于官方 stage1 没有公开 GT，先用程序生成带阶段真值的轨迹：直线、爬升、下降、加速、减速、转弯、盘旋、绕飞及组合序列，并加入采样不均匀、缺点、噪声和异常点。真实 stage1 样本只用于开发分析和人工复核，不用于直接微调成题面记忆。

### 6.2 区域理解

区域题优先由几何引擎产生事实表，模型负责理解“到访、进入、离开、累计停留、从区外进入次数、进入顺序”等题目统计口径，并完成四选一。

处理顺序：

1. 解析样本起始时间、相对时间和多边形坐标；
2. 轨迹点按时间排序；
3. 用 Shapely 判断点内外和线段跨界；
4. 计算进入、离开、停留、区外进入次数和顺序；
5. 将相对秒数转换成起始时间对应的 UTC 时间；
6. 将事实表和选项交给 Qwen3 判别；
7. 用规则检查答案是否引用不存在的区域或时间。

区域引擎必须先用人工构造的矩形、边界点、起点在内、多次进入和同时区域样例进行验证，再接入真实题目。

## 7. task2 落地方案

### 7.1 离线航迹缓存

对 2,000 条轨迹一次性完成：

1. CSV UTF-8 读取；
2. 按 `航迹编号` 分组、按 UTC 时间排序；
3. 重复点、时间跳变和异常点标记；
4. 计算运动特征；
5. 计算全局统计：起止时间、持续时长、包围盒、高度/速度范围；
6. 计算行为事件序列；
7. 对查询区域计算进入、离开和停留事件；
8. 生成机器 JSON 摘要和检索文本摘要。

缓存至少包含三个层次：

- `tracks_normalized`：标准化点序列；
- `track_facts`：机器可执行事实；
- `track_documents`：供模型和后续向量检索使用的短摘要。

2,000 条航迹规模适合先完整扫描和缓存，不先引入向量数据库，减少依赖和调试面。

### 7.2 查询解析

Qwen3 只做自然语言到 IR 的转换，重点解析：

- 时间范围和日期；
- 高度、速度范围；
- 区域正向条件；
- 区域否定条件；
- 行为类型；
- 行为顺序和允许间隔；
- `top_k`。

解析结果经过 Pydantic/schema 检查、单位归一化和逻辑检查。例如最小值大于最大值、结束时间早于开始时间、区域正负集合冲突时必须报错或修复。

### 7.3 硬过滤

对所有轨迹按以下顺序执行：

1. 时间窗口；
2. 高度和速度范围；
3. 必须经过区域；
4. 必须不经过区域；
5. 已识别的行为必需条件。

不满足硬条件的轨迹直接淘汰。语义相似度不能把硬条件不满足的轨迹重新排回候选集。

### 7.4 行为顺序匹配

将轨迹和查询都表示成带时间的行为事件：

```text
event = {type, start, end, confidence}
```

“先 A、随后 B”必须同时满足：A 存在、B 存在、A 结束时间早于 B 开始时间，并满足允许间隔。排序分数由事件存在、顺序、时间接近度和特征相似度组成。

### 7.5 排序阶段

分三档实现：

1. **结构化基线**：硬过滤后按条件匹配度、行为顺序和数值距离排序；
2. **可选 BGE-M3 召回**：仅对硬过滤候选做语义召回；
3. **可选 reranker**：对前 50–100 条候选做交叉编码器重排。

新增模型必须在内部验证集上证明 Recall@5 或 nDCG@10 稳定提升，并确认赛事对第二个专用模型的参数口径。

## 8. Agent 和模型调用边界

首版 Agent 采用有界流程，不采用无限制自主循环：

### task1

- 轨迹摘要由工具生成；
- Qwen3 完成选项语义判别；
- 失败时最多一次 JSON 修复；
- 事实冲突时记录并进入错误日志。

### task2

- Qwen3 生成查询 IR；
- 确定性过滤和排序工具执行候选计算；
- 只有在需要语义排序时才调用可选检索模型；
- 最终由提交模块生成 Top-K。

所有模型调用记录：模型版本、提示词版本、输入摘要哈希、原始输出、解析结果和耗时。这样可以复现一次错误，而不需要把完整原始轨迹重复塞给模型。

## 10. 评测设计

官方 stage1 不提供公开 GT，因此内部评测分三层：

### 10.1 确定性单元评测

- 时间排序和相对时间换算；
- 航向角 0/360 环绕；
- 多边形边界和跨界插值；
- 起点在区域内不计新进入；
- 重复进入和同时区域事件；
- 查询范围和否定条件逻辑。

### 10.2 程序生成评测

由轨迹生成过程保留阶段标签、区域事实和查询正例，生成 hard negative，计算：

- task1 选项准确率；
- 区域事件字段准确率；
- task2 Recall@5、Recall@10、nDCG@10；
- top_k 长度和输出格式通过率。

### 10.3 真实 stage1 人工复核

对 50 条分段、50 条区域、50 条检索样本进行内部复核，记录：

- 模型理解错误；
- 时间换算错误；
- 区域边界错误；
- 否定条件错误；
- 行为顺序错误；
- 输出格式错误。

真实 stage1 的人工判断只用于研发定位，不能被写成样本编号到答案的映射表。

## 11. 资源和运行策略

### 11.1 模型

- Qwen3-4B：最终主模型候选；
- Qwen3-1.7B：快速回归和低显存候选；
- `float16`；

### 11.2 缓存

- 航迹标准化缓存；
- 区域事件缓存；
- 模型权重缓存；
- 查询 IR 缓存；
- 版本化的 prompt 和配置。

缓存文件不直接提交 Git，使用 `.gitignore` 和配置路径管理。

### 11.3 容器工作区

当前 `/workspace/repo` 位于容器自身存储层。`docker compose stop/start` 可以保留，但 `docker compose down` 或重新创建容器可能丢失仓库和 Git 配置。进入正式开发前，应把 `/workspace/repo` 改为命名卷或主机绑定目录，并把 Git HTTP 代理配置写入运行配置；否则仓库同步环境不可复现。

第一轮的成功标准是：环境可复现、数据可读取、缓存路径稳定、输出 schema 已冻结。此时还不要求模型给出高分答案。

## 13. 最终可提交形态

```text
加载本地 Qwen3
  ↓

  ↓

  ↓
task1：事实摘要 + 选项判别

  ↓
校验样本完整性、字段和 JSONL 编码
  ↓
输出 traj_result.jsonl
```

最终版本必须满足：

- 不依赖闭源在线模型；
- 不使用测试样本答案映射或人工修改答案；
- 关键数值和几何关系可由中间事实追溯；
- task2 的硬条件不会被语义排序推翻；
- 所有样本恰好输出一条记录；
- 输出文件符合 UTF-8、逐行 JSON 和官方字段要求；
- Docker 中可离线加载模型和运行推理。
