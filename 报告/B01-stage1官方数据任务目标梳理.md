## 1. 数据包定位

本报告依据官方发布版目录中的 README，以及对样例文件和提交示例的核对整理。

数据包目录：

README 明确说明，stage1 主要用于帮助参赛队伍熟悉数据格式、赛题任务和提交方式。它包含：

- task1 航迹理解；

因此，stage1 是一套完整的初赛任务熟悉和本地开发数据包，但不能仅凭它断言后续正式测试集的规模和具体内容完全相同。

## 2. 初赛总体任务目标

B01 初赛的实际目标不是训练一个开放式聊天机器人，而是构建一个离线运行的航迹语义理解与跨模态检索 Agent，对官方输入样本逐条生成结构化答案。

初赛包含两个一级任务：

1. **task1：航迹理解**
   - 输入一条航迹及文本问题；
   - 根据航迹的时序、位置、高度、速度、航向和区域关系完成判断；
   - stage1 中两个子任务均为四选一单选题；
   - 每道题只需要输出一个选项结果。

2. **task2：跨模态检索**
   - 输入自然语言检索条件、可选的区域约束和航迹库；
   - 从约 2000 条候选航迹中找出满足条件的航迹；
   - 按相关度排序输出 Top-K 航迹编号；
   - stage1 的 top_k 取值范围为 10—15。

主办方会保留正确答案用于机器评测。stage1 的题目文件没有公开答案字段；随包提供的 traj_result.jsonl 是格式示例，其中的选项和航迹编号是占位内容，不是实际答案。

## 3. task1：航迹理解

### 3.1 共同输入

task1 两个子任务都以单条航迹为核心输入。航迹数据包含：

- 航迹编号；
- 航迹起始绝对时间，ISO 8601 UTC；
- 速度单位，均为 m/s；
- 点位序列。

每个点位包含：

- 时间戳：相对于航迹起点的秒数，不是绝对时间；
- 经度、纬度：十进制度，经度在前、纬度在后；
- 高度：米；
- 速度：m/s；
- 航向角：0—360 度，正北为 0 度，顺时针增加。

系统需要同时理解相对时间和绝对时间：

- 点位序列中的时间戳用于分析轨迹阶段和事件顺序；
- 航迹起始时间用于把相对时间换算成题目选项中的绝对时刻。

### 3.2 task1-分段理解

文件：task1/01_segment_questions.jsonl，共 50 条。

目标是识别一条航迹在不同阶段的飞行形态，并判断这些形态的先后顺序。题目可能涉及：

- 各阶段飞行形态顺序；
- 平面机动方式及顺序；
- 高度变化阶段；
- 速度调节过程；
- 高度层、速度层或轨迹层的分段序列。

典型处理过程：

    轨迹点排序
      → 计算高度、速度、航向和位置变化
      → 识别连续阶段及阶段边界
      → 将阶段序列与 A/B/C/D 选项比较
      → 输出唯一选项

这项任务的核心是“时序分段理解”，不是只看单个点，也不是只做静态分类。

### 3.3 task1-区域理解

文件：task1/02_region_questions.jsonl，共 50 条。

相比分段理解，输入增加 2、4 或 6 个多边形区域。目标是根据整段航迹判断：

- 是否到访各区域；
- 进入时刻；
- 离开时刻；
- 累计停留时长；
- 从区外进入的次数；
- 多个区域的进入顺序；
- 重复进入是否发生以及重复进入的顺序。

README 特别规定了统计口径：

1. 只统计航迹时间范围内的进入、离开和停留事件；
2. 航迹起点已经在区域内时，不算一次新的进入；
3. 进入顺序按时间排列；
4. 重复进入要重复列出；
5. 同一时刻进入多个区域时，按区域在输入中的顺序排列；
6. 题干使用相对时刻，选项使用起始时间换算后的绝对时刻。

典型处理过程：

    轨迹点按时间排序
      → 点在多边形内/外判断
      → 检测内外状态变化
      → 计算进入、离开、停留和顺序
      → 将相对时间换算为绝对时间
      → 与四个选项整体比对
      → 输出唯一选项

这里最容易出错的是边界、采样点之间的穿越、起点已在区域内、重复进入、同刻排序和时间换算。不能只用“轨迹点是否落在区域内”简单代替完整事件判断。

## 4. task2：跨模态检索

### 4.1 输入

文件：task2/01_retrieval_questions.jsonl，共 50 条。

每条检索问题包含：

- 样本编号；
- 区域约束，可为空；
- 自然语言文本查询；
- top_k，建议返回数量为 10—15。

task2 航迹库文件：task2/02_tracks.csv。

航迹库字段：

- 航迹编号；
- 时间戳，绝对 UTC 时间；
- 经度、纬度；
- 高度；
- 速度。

README 给出的数据规模是约 2000 条航迹、483657 个点，每条航迹包含 25—1101 个点。

### 4.2 查询语义

检索条件可能同时包含：

- 时间；
- 高度；
- 速度；
- 一个或多个区域；
- 飞行行为；
- 多阶段行为顺序；
- 区域否定条件。

例如，查询可能要求：

- 在某个时间段起始；
- 经过区域 A；
- 不经过区域 E；
- 低速移动；
- 先盘旋绕飞，随后加速。

因此 task2 是“结构化时空过滤 + 轨迹行为理解 + 相关性排序”的组合任务，不能只做文本关键词匹配。

### 4.3 轨迹库预处理要求

README 明确提醒：

- 同一航迹的点不保证严格按时间递增；
- 在计算速度、顺序和停留之前，必须按时间戳排序；
- 可能存在时间跳变；
- 可能存在坐标异常点；
- 建议先去重并处理异常点；
- 相同航迹编号的记录需要分组使用。

因此，task2 的第一步不是直接建向量索引，而是建立规范化的轨迹库：

    CSV 读取
      → 按航迹编号分组
      → 时间排序
      → 去重和异常点处理
      → 计算轨迹摘要和事件特征
      → 建立可检索索引

### 4.4 典型检索流程

    文本查询解析
      → 提取时间、高度、速度、区域、否定和行为约束
      → 使用确定性几何/时序工具做候选过滤
      → 对候选航迹生成行为摘要
      → 用本地模型完成语义匹配和重排序
      → 返回 top_k 条有序航迹编号

初赛评测使用 Recall@5 和 nDCG@10：

- Recall@5 关注正确航迹是否进入前 5 名；
- nDCG@10 关注前 10 名的排序质量；
- 不能只返回满足条件的航迹集合而不排序；
- 返回数量应结合输入的 top_k，不能固定写死为 10。

## 5. 统一提交目标

README 要求所有任务结果合并到一个 traj_result.jsonl 文件，每行一个完整 JSON 对象，样本编号必须对应输入样本。

按 README 的文字说明：

- task1 两个子任务使用选项字段，填写单个 A/B/C/D；
- task2 使用结果字段，填写按相关度排序的航迹列表；
- 文件 UTF-8 编码；
- 每行必须是独立 JSON；
- 样本编号不能重复、不能遗漏；
- 不添加注释。

但是，发布版目录中实际提供的 traj_result.jsonl 示例是：

    {"样本编号": "seg_000001", "结果": "<A/B/C/D>"}
    {"样本编号": "region_000001", "结果": "<A/B/C/D>"}
    {"样本编号": "retrieval_000001", "结果": [{"序号": 1, "航迹编号": "traj_XXXXXX"}]}

这与 README 中“task1 使用选项字段”的文字存在冲突。此前赛题 PDF 和官方截图也展示过 task1 使用“结果”字段的形式。因此，在正式提交前必须以官方提交校验器、最新代码模板或赛事方书面答复为准。

在没有官方澄清前，工程上应：

1. 将答案生成层与字段名配置分离；
2. 同时支持 task1 的 选项 和 结果 两种字段模式；
3. 不要把字段名硬编码到业务算法中；
4. 先用官方校验工具或提交平台做一次格式验证。

## 6. 对 Agent 设计的直接结论

### 第一层：确定性轨迹工具

应优先实现：

- 时间排序；
- 坐标和时间规范化；
- 速度、高度、航向变化计算；
- 阶段分割；
- 多边形内外判断；
- 进入/离开事件检测；
- 停留时长和进入顺序计算；
- 查询中的时间、速度、高度和区域过滤。

这些工具负责稳定、可复现的数值和几何计算。

### 第二层：本地模型语义判断

模型主要负责：

- 将轨迹特征组合成飞行阶段语义；
- 将文本中的行为描述映射到轨迹行为；
- 处理“先……随后……”等复合表达；
- 对候选轨迹进行语义重排序；
- 判断否定条件和复杂查询的整体满足程度。

### 第三层：结构化输出与校验

输出层负责：

- 选择正确字段名；
- 生成单个选项字母或有序航迹列表；
- 检查样本编号完整性和唯一性；
- 检查 Top-K 数量、序号连续性和航迹编号有效性；
- 确保 UTF-8 和 JSONL 格式合法。

## 7. 对此前判断的修正

stage1 README 使任务边界更加明确：

1. 初赛不是一个泛化的“航迹问答”任务，而是 100 条 task1 选择题加 50 条 task2 检索问题；
2. task1 包含“分段理解”和“区域理解”两个独立子任务；
3. task2 提供了明确的 2000 条航迹候选库，开发阶段可以本地建立真实索引；
4. task1 的区域题比此前截图显示的单一示例更完整，重点考察事件统计口径；
5. task2 明确包含多区域、否定条件和行为序列，检索解析难度高于简单时间/区域过滤；
6. stage1 是用于熟悉格式和开发的官方数据包，不能默认其题目答案会随包提供；
7. 提交字段存在 README 文字与 traj_result.jsonl 示例不一致的问题，必须在开发早期解决。

---

## 8. 当前最合理的开发顺序

1. 先实现 JSONL 读取、样本分类和提交文件校验；
2. 实现 task1 分段理解的数值特征和选项匹配；
3. 实现 task1 区域理解的多边形事件统计；
4. 对 task2 航迹库做分组、排序、去重和异常处理；
5. 实现 task2 的时间、速度、高度和区域候选过滤；
6. 增加行为序列和否定条件解析；
7. 增加本地模型重排序；
8. 最后统一处理 task1/task2 的答案字段和官方格式校验。

第一阶段不需要先做复杂的通用 Agent。先把 150 条 stage1 样本和 2000 条航迹库变成可重复处理、可解释、可验证的管线，更符合初赛任务目标。
